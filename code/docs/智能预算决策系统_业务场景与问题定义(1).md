# 智能预算决策系统 — 业务场景与问题定义

> 本文档用于向团队成员、项目干系人及技术合作方解释：我们正在解决什么问题，为什么这个问题有难度，以及我们期望的系统长什么样。
>
> **版本：v2.3 | 2026-04-20**

---

## 一、业务背景

### 1.1 服务对象

我们是乙方投放团队，服务多个渠道和甲方客户（渠道如 vivo、oppo 等）。**每个客户的预算和优化目标是完全独立的**，不存在跨客户的预算竞争：

```
客户A（vivo）
  └─ 预算池A → 只在客户A的产品间分配

客户B（oppo）
  └─ 预算池B → 只在客户B的产品间分配

客户C（其他）
  └─ 预算池C → ...
```

系统为每个客户**独立建模、独立求解**，每天对所有客户批量运行优化器。

### 1.2 核心目标

每个客户的投放目标是：

> **在月度活跃 ROI ≥ KPI（硬约束）的前提下，最大化该客户的月度广告消耗规模。**

- **KPI**：月度活跃 ROI 目标（默认 105%，客户可能随时调整）
- **消耗规模**：本月花出去的总广告费
- **月度活跃 ROI**：本月累计回收 ÷ 本月累计花费
- **产品规模**：单个客户有几十到上百个产品

举例：本月花了 100 万，月末 ROI 105%，意味着本月回收了 105 万。其中约 100 万来自本月新增用户在本月释放的全部回收（D1 + D3 + D7 + D14 + D30 等在本月落地的所有变现），约 5 万来自历史 Cohort（本月之前新增的用户）在本月的活跃变现。

## 二、这不是一个普通的优化问题

### 2.1 回收是滞后的，不是即时的

广告变现的特点是：**今天花出去的钱，不会今天全部收回来。**

举例一批用户今天新增，其变现回收的累积增长曲线如下（D1 为基准 = 1.00）：

| 时间点 | Dn / D1 累积倍率 | 含义 |
|---|---|---|
| D1 | 1.00 | 首日回收为基准 |
| D3 | ~1.29 | 到第3天累计变现为首日的1.29倍 |
| D7 | ~1.38 | 到第7天累计变现为首日的1.38倍 |
| D14 | ~1.44 | 到第14天累计变现为首日的1.44倍 |
| D30 | ~1.44 | 到第30天累计变现为首日的1.44倍 |

举例：若某产品 D1 ROI = 69%，则该产品用户到 D7 的累积回收率 = 69% × 1.38 ≈ 95%。

这意味着：

- **月初投的钱**：回收窗口长，到月末能完整释放，ROI 贡献高
- **月末投的钱**：回收窗口短，到月末只来得及回收 D1，ROI 贡献低

同样花 1 万块钱，月初投和月末投，对月末 ROI 的贡献完全不同。

### 2.2 每天数据在变，最优策略也在变

每个月有 30 天左右，每天会发生几件事：

- 新增一批用户，产生新的 Cohort
- 历史 Cohort 继续释放变现
- D1 回收率会随流量质量波动
- 月度累计 ROI 逐渐收敛

前天算出来的最优预算，今天可能已经不够优了。系统需要"每天重新算一次"。

### 2.3 月末在做跨期决策，不只是当日决策

到了月末几天，真正的博弈才浮出水面：

> **月末多花，ROI 贡献低，当月可能不达标；但多花的钱会在下个月释放历史回收，让下个月起点更高。**

这是典型的**跨期权衡**：

```
本月多花 100 元
    ↓
本月月末 ROI 轻微下降（比如从 106% 降到 104%）
    ↓
下个月这批用户释放历史回收
    ↓
下个月可多花 ~260 元（杠杆约 2.6 倍，视倍率曲线而定）
```
此处为举例，非确定值
问题是：这个交换划不划算？有没有边界？什么时候该蓄力，什么时候该保达标？

## 三、问题的本质：六层决策体系

我们面对的问题不是"找一个最优解"，而是**设计一套整盘规模最大化的动态决策机制**。

核心问题拆解为**六层**，按从粗到细的顺序：

---

### 3.1 第一层：KPI 层（做什么）

**做什么**：确定月度 ROI 目标，以及各产品的优先级。

**关键特点**：

- KPI 由客户决定，可能随时调整
- 系统必须能**动态响应 KPI 变化**，重新求解
- 不要求每个产品单独达标，允许**整体达标即可**（A级产品可以补贴C级产品）

---

### 3.2 第二层：时间层（什么时候冲）

**做什么**：确定每个时间窗口的预算优先级。

**IAA 产品的节假日效应**：

| 时间类型 | 特点 | 策略含义 |
|---|---|---|
| **普通工作日** | 基准流量 | 均匀消耗或按整体节奏 |
| **周末** | 流量高 x% | 用户活跃，变现好，可适当多投 | 周六日后续较弱，需做高首日ROI，可参考历史数据 | 
| **小长假（五一/端午/清明）** | 流量高且持续多天 | 提前蓄量、节中高投放 |
| **暑假/寒假** | 持续时间长，量级大 | 长期预算规划窗口 |
| **电商节（618/双11/双12）** | 广告主多、ECPM 高 | 高变现窗口，可多投 |

**节假日识别** → 影响：
1. 当天的变现回收预测（D1/D3 曲线会变）
2. 次日的预算建议
3. 跨节假日的天数窗口计算

---

### 3.3 第三层：配置层（钱分给谁）

**做什么**：把预算分配到各产品，确定比例。

**全局 ROI 池化（Portfolio Optimization）**：

> 系统将客户旗下的所有产品视为**单一 ROI 资产组合**，决策标准基于"全局盈余分配"。

核心逻辑：

- 不再要求每个产品单独 ROI 达标
- 只要 A 级产生的超额利润足以覆盖 C 级的亏损，且**整体 ROI ≥ KPI**，系统就应通过 A 级补贴 C 级的方式最大化整盘消耗规模
- 分配优先级：**边际收益最高**的产品优先拿预算

**注意**：单产品低 ROI 不会直接破坏媒体账号权重，"补贴 C 级有风险"在实操中不成立。但在亏损可控的前提下进行。

| 产品 | D1 | M30 | 终生ROI | 特点 |
|---|---|---|---|---|
| A级（果冻美食屋） | 69.81% | 1.509 | 105.34% | 首日回收快，短期效率高 |
| C级（生存大作战） | 62.63% | 1.637 | 102.55% | 首日慢，但尾部增长高 |

A级优先拿预算；C级在A级有余量时补充，但必须在已知消耗上限（cap）内进行（见第六章P0约束）。

---

### 3.4 第四层：节奏层（月内每天怎么排）

**做什么**：确定月内每天的预算节奏，以及何时从"达标模式"切换到"规模最大化模式"。

**核心概念：ROI 盈余驱动的月末释放（Surplus-Driven Release）**

月末低 ROI 不是因为流量质量变差，而是**回收窗口缩短导致的统计性下降**——月末几天只能计入 D1-D3 回收，D7 以后的变现会跨到下个月。

**决策逻辑**：

- 判定标准：若月度累计活跃 ROI **远高于** KPI（建议 ≥ KPI + 5pp），系统应切换至"规模最大化模式"
- 此时的决策：月末增加的预算虽然会拖累本月累计 ROI，但其产生的长线 LTV 将提升下月初始回收水位（跨月飞轮）
- 系统的核心任务：实时精算"在不突破 KPI 底线的前提下，本月还能释放多少消耗规模"

**两种节奏对比**：

| 节奏 | 逻辑 | 适用场景 |
|---|---|---|
| **U型（盈余释放型）** | 月初冲量 → 月中平稳 → 月末在盈余充足时蓄力 | 有 ROI 盈余，追求跨月增长 |
| **均匀** | 每天等量消耗 | 无盈余空间，求稳优先 |

> 注：月末释放≠无限制投放，KPI底线始终是硬约束。

---

### 3.5 第五层：风控层（出了偏差怎么办）

**做什么**：在系统里内置稳健性，不只是事后告警。

**执行层：弹性控制（Adaptive Smoothing）**

死板的日耗波动限制（如每日涨跌20%阈值）会阻断流量高峰期的放量节奏（如从2万跳涨至7万）。应引入**环境缩放因子（Scale Factor）**：

```
今日预算上限 = min(昨日消耗 × Scale_today / Scale_yesterday × 弹性系数, 绝对上限)
```

- 当系统识别到节假日流量红利时，应自动抬高波动上限，确保规模释放不受算法拦截
- 同时保留绝对上限，防止某日异常导致推荐值失控

**两类风险**：

| 风险 | 触发条件 | 响应机制 |
|---|---|---|
| **产品能力下滑** | 连续 N 天 D1 低于达标 D1 | 自动降权 → 缩减该产品预算 |
| **流量异常波动** | 当日变现偏离预测 ±20% | 切换保守预算（payback_budget） |
| **KPI 调整** | 客户修改目标 | 立即重新求解，全量重算 |
| **累计 ROI 预警** | 预测月末 ROI 低于 KPI 3pp+ | 触发缩减建议 |

---

### 3.6 第六层：决策排序层（先定什么、后定什么）

**核心难题：动态轨迹求解**

解决"每天花多少钱对本月最好"的本质是**求解全月消耗面积的最大化**。

- 预测变量：每日预测 D1，以及基于剩余天数的本月内回收倍率
- 动态调整：系统必须在每日 T+1 数据完整回传后（次日中午12:00），重新计算剩余日期内的所有决策变量，以修正前一日的波动误差

这是最关键的结构问题：**各层的求解顺序不同，结果完全不同。**

**三种求解路径**：

| 方案 | 顺序 | 优点 | 缺点 |
|---|---|---|---|
| **A：先产品后时间** | 比例分完 → 再排节奏 | 实现简单 | 节假日窗口可能没有足够预算空间 |
| **B：先产品后时间 + 时间调整** | 先分产品比例，再按节假日微调 | 实现较简单 | 非联合最优，可能错过最优节假日窗口 |
| **C：联合求解** | 产品×时间一起建模 | 数学最优 | 需要专业求解器（推荐 Gurobi/CPLEX） |

**推荐方案C**，理由：

1. **规模驱动**：单客户有几十到上百个产品，产品×时间 = 数百个决策变量，这正是专业求解器最擅长的规模，秒级出结果
2. **真实最优**：联合建模才能找到产品分配和时间节奏的最优组合，方案A/B都是近似
3. **技术成熟**：Gurobi/CPLEX 是成熟的商业求解器，Python 有 PuLP/Pyomo 接口，实现成本可控

**实现成本说明**：方案C需要引入求解器（Gurobi/CPLEX），比 Excel/JS 实现复杂，但这不是技术障碍，而是工程选择。随着产品数增加，方案C的收益远大于实现成本。

```
推荐实现路径：
  Step 1（时间层）：确定节假日日历，标注每个时间窗口的类型
  Step 2（联合求解）：用 Gurobi/PuLP 建模，产品×时间联合求解
  Step 3（每日滚动）：每天更新数据，重新求解，更新建议
```

## 四、问题总结：完整的数学定义

```
目标：整盘月度规模最大化

决策变量：
  d(p, t) = 产品p在时间窗口t的每日预算分配
  其中 t 按节假日类型细分

目标函数：
  max Σ d(p,t)
  （在 ROI 约束下，最大化全月消耗面积）

约束：
  - 月度活跃 ROI ≥ KPI（动态，可能随时变）
  - 各产品消耗上限 cap(p)（需通过扩量实验验证，见第六章）
  - 整体 ROI 池化（A级补贴C级，全局达标即可）
  - 弹性执行约束：d(p,t) ≤ min(d(p,t-1) × Scale_t/Scale_{t-1} × 弹性系数, 绝对上限)
  - 当月度累计 ROI ≥ KPI + 5pp 时，切换至规模最大化模式（释放月末盈余）

求解方法：
  Step 1：节假日日历标注（周末/小长假/暑假/春节/电商节），设定各类型 scale 因子
  Step 2：多产品×时间联合建模（Gurobi/PuLP）
  Step 3：每日 T+1 数据回传后滚动重求解（MPC），修正波动误差
  Step 4：跨月飞轮影响纳入月末决策（量化下月收益贡献）
```

## 五、我们期望的系统是什么样子

### 5.0 使用对象与操作方式

**使用对象**：投放运营人员

**操作方式**：当前阶段为**手动操作**——系统每天输出建议，运营人员根据建议手动调整各产品的日预算。未来系统规划对接广告平台做自动出价/调预算。

**核心交互**：运营每天打开系统 → 查看今日建议 → 手动在各广告后台调整预算 → 系统次日根据实际数据滚动更新

### 5.1 每日输出

每天数据更新后，系统应输出：

| 输出项 | 含义 | 字段注释 |
|---|---|---|
| **月度累计消耗预测** | 基于当前实际消耗 + 剩余天数建议消耗，预测月末总规模 | = 已发生消耗 + Σ(剩余每天建议消耗)。每天数据更新后自动重算，反映最新实际消耗对月度总规模的影响 |
| **今日分产品分版位建议预算** | 每个产品在各版位的建议预算分配 | 版位包括：**商店**、**联盟**（联盟流量）、**智能投放**（自动优化版位）。不同版位D1和倍率不同，需分别建模 |
| **今日 D1 回收目标** | 今天花的钱预计首日能回收多少 | = 建议预算 × 预测 D1%，是判断当日投放效率的基准 |
| **今日历史回收预估** | 今天历史用户（本月之前新增的用户）预计贡献多少变现 | = 当日广告变现 - 新增用户 D1 变现。是判断今日 ROI 能否达标的关键分子 |
| **月度预测 ROI** | 按当前节奏，月末预计 ROI 是多少 | = (已发生回收 + 剩余天数预测回收) / (已发生消耗 + 剩余天数预测消耗) |
| **月度预测总规模** | 按当前节奏，月末预计总消耗规模 | = 月度累计消耗预测的最终值，与 ROI 预测联动呈现 |
| **产品分级诊断** | 各产品的效率状态、达标缺口、调优方向、改善窗口 | 见下方字段注释 |
| **风险预警** | 产品能力下滑 / 流量异常的自动告警 | 见下方字段注释 |
| **KPI 调整响应** | KPI 变化后立即重新计算并提示影响 | 如 KPI 从 105% 调整为 102%，系统重新求解并输出：新建议预算、月末 ROI 变化幅度、需要缩减/释放的金额 |

**「产品分级诊断」字段注释**：

| 字段 | 含义 | 示例 |
|---|---|---|
| 效率状态 | 产品的变现效率等级。判断标准：预测 D1 vs 达标 D1（= KPI ÷ M30）。高于达标 D1 为 A 级（高效），接近为 B 级（中等），低于为 C 级（低效但长尾可能补回） | A级：D1=69%，达标D1=66% → 超额3pp |
| 达标缺口 | 产品当前累计 ROI 距离 KPI 目标还差多少个百分点 | 当前ROI 98%，KPI 105%，缺口7pp |
| 调优方向 | 基于诊断结果建议的操作方向：加量（效率好）、维持（达标中）、减量（拖累整体） | A级产品 → "加量"；C级产品 → "减量或维持观察" |
| 改善窗口 | 产品距离"无法挽救"还有多少天。如果持续低效，超过这个窗口后即使归零也不再影响当月 | 剩余20天 → 还有调整空间；剩余3天 → 基本定型 |

**「风险预警」字段注释**：

| 预警类型 | 含义 | 判断标准示例 |
|---|---|---|
| 产品能力下滑 | 产品的 D1 回收率持续低于预期，投放效率在恶化 | 连续 N 天（默认3天）实际 D1 低于预测 D1 的 90% |
| 流量异常波动 | 当日变现金额严重偏离模型预测值 | 当日实际变现偏离预测值 ±20% |

### 5.2 核心能力

| 能力 | 说明 |
|---|---|
| **节假日自动识别** | 对接日历，自动标注未来节假日类型（周末/小长假/寒暑假/电商节等），人工补充偶发流量高峰期 |
| **滚动预测** | 每天用新数据更新 LTV 曲线，重新预测剩余天数的回收 |
| **多产品联合求解** | 在 ROI 约束下，按时间节奏分配各产品预算 |
| **分版位建模** | 不同版位（商店/联盟/智能投放）的 D1 和倍率曲线不同，系统分别建模、分别输出建议 |
| **KPI 动态响应** | KPI 变化立即触发全量重算 |
| **风控内置** | 产品能力下滑 / 流量异常自动降权，不只是告警 |
| **跨期评估** | 量化"月末多花1元，对下个月 ROI 的边际贡献" |
| **数据接口对接** | 系统通过数据中台接口自动获取投放数据（消耗、变现等） |

### 5.3 执行节奏（机制设计）

```
每天：
  1. 从数据中台接口拉取当日数据（消耗、各日回收等）
  2. 更新节假日日历状态
  3. 更新 Cohort 状态
  4. 滚动更新 LTV 曲线和倍率参数（含各版位独立曲线）
  5. 检查 KPI 是否变化 → 如有则全量重算
  6. 用新状态重新求解未来剩余天数的最优预算轨迹
  7. 输出今日各产品建议预算 + 分版位建议 + 历史回收预估
  8. 记录当日状态，供明天使用
  9. 同时更新月度累计消耗预测和月度预测 ROI（基于最新实际消耗 + 新建议轨迹）
每月末：
  10. 评估跨月飞轮效果
  11. 用实际数据校准模型参数
```**滚动重算说明**：第9步是关键——每天数据落地后，用真实已发生消耗替换昨天的预测值，再结合剩余天数的最新建议，重新推算月末总规模。随着月底临近，预测区间缩短，预测值逐步收敛至确定性结果。
---

## 六、建模假设清单

建模之前，必须先说清楚：**哪些假设是确定的、哪些还需要验证**。

用词不严谨会误导后续决策——把"理论推断"当成"实证结论"，会导致模型上线后翻车。

---

### 确定性分级说明

| 等级 | 含义 | 建模建议 |
|---|---|---|
| **✅ 已验证** | 有数据支撑，在我们业务上确认成立 | 直接进模型 |
| **⚠️ 待验证** | 理论逻辑成立，但未在我们数据上实测 | 先做 A/B 测试或回测，验证后再进模型 |
| **❓ 待评估** | 可能有影响，但不确定在我们场景下是否显著 | 先评估影响范围（impact × probability），高分再建模 |

---

### ✅ 已验证的假设

以下是我们有数据或数学证明支撑的建模基础：

| 假设 | 证据 |
|---|---|
| **回收是滞后的** | D1 只能回收 60~70%，D30 才接近 100% |
| **LTV 曲线形态固定** | 各产品的 Dn/D1 倍率稳定（D3 ≈ 1.29×，D7 ≈ 1.38×，D30 ≈ 1.44×） |
| **月末投钱 ROI 贡献低** | 月末只有几天回收窗口，D1 之后的多日回收跨不到当月 |
| **月初比月末 ROI 贡献高** | 月初投的用户，到月末释放窗口完整 |
| **节假日变现好于平日** | 周末、小长假、电商节等时间点回收明显提升 |
| **不同产品效率不同** | A 级产品 D1 高（69%），C 级 D1 低（62%），倍率曲线也不同 |

---

### ⚠️ 待验证的假设

以下假设逻辑上成立，但需要在我们的数据上验证后再建模：

| 假设 | 验证方法 | 什么时候会翻车 |
|---|---|---|
| **ROI 随消耗增加而递减** ⭐ | 用历史扩量数据画"ROI vs 消耗"散点图，看是否存在明显下降趋势 | 当产品消耗超过精准人群规模时，ROI 会快速下降；这是防止求解器"全押单一产品"的核心物理约束 |
| **产品存在流量上限（cap）** ⭐ | 逐步扩量测试，找到 ROI 开始显著下降的拐点 | 如果 cap 未知，推荐预算会远超实际可投量；即使补贴 C 级产品，也必须在已知 cap 内进行 |
| **扩量后 LTV 曲线会变差** | 对比低消耗期和高消耗期的倍率曲线，看 D7/D1 是否下降 | 如果曲线变差但模型用固定曲线，会系统性高估收益 |
| **节假日 scale 因子可量化** | 统计历史节假日 vs 平日的 D1 比值，算出各类型的修正系数 | 如果 scale 因子不准，预算会错误分配到高/低价值窗口 |

> ⭐ 注：ROI 递减 和 cap 这两项已列为**下周最高优先级验证项**。虽然保留"待验证"标签，但一旦验证通过，应立即升级为 P0 核心建模约束。
| **周末 D1 高于平日** | 统计最近 4~8 周的周末 D1 vs 工作日 D1，算出修正系数 | 如果不区分周末，预测会有 ±10~15% 的系统性误差 |

---

### ❓ 待评估的假设

以下假设可能对模型有影响，但不确定在我们场景下是否显著：

| 假设 | 评估问题 | 如果显著，该怎么处理 |
|---|---|---|
| **归因窗口是否对齐** | 平台归因口径（1天/7天）和我们变现回收口径（D1+D3+D7+...）是否一致？ | 需要对齐口径，否则优化目标和实际 ROI 永远对不上 |
| **渠道是否有最低消耗/速率限制** | 每个渠道/账户是否有单日最低消耗、预算调整速率限制？ | 预算约束里加 `d(p,t) - d(p,t-1) ≤ Δ` |
| **产品间是否存在人群竞争** | 同客户不同产品是否可能抢同一批用户？ | 给同类产品加"总 cap"，或用历史数据验证是否存在竞争 |
| **P20 悲观值 vs 均值** | D1 波动多大？用均值还是悲观值，对月末 ROI 风险敞口影响多大？ | 用 P20 代替均值作为基准，降低边界策略的翻车概率 |

---

### 结论：先建什么

```
✅ 直接建（已验证）：
  - LTV 曲线（D1→D3→D7→D14→D30 倍率）
  - 剩余时间价值修正（天数 × 倍率）
  - 月度 ROI 约束

⚠️ 验证后再建（待验证）：
  - 边际 ROI 曲线（替代平均 ROI）
  - 产品流量上限（cap）
  - 节假日 scale 修正系数
  - 周末 scale 修正系数

❓ 评估后再决定（待评估）：
  - 归因窗口对齐
  - 渠道执行约束
  - P20 悲观值
```

## 八、技术关键词

- **LTV**：Life Time Value，用户终生变现价值
- **Cohort**：按新增日期分组的用户群
- **D1/D3/D7/D14/D30**：用户新增后第 N 天的累积回收节点
- **M30**：30 天累积倍率，即 D30 / D1
- **倍率曲线**：描述用户从 D1 到 D30 各节点的回收增长曲线
- **月度活跃 ROI**：当月变现 ÷ 当月消耗
- **跨月飞轮**：月末蓄力 → 下月高起点 → 下月可多花
- **MPC**：模型预测控制，滚动优化的经典框架
- **IAA**：In-App Advertising，应用内广告变现
- **节假日效应**：周末/五一/暑假/春节/电商节等带来的流量和变现变化
